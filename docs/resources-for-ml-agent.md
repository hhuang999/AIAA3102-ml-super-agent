# MLEvolve 类 ML Agent 的资源方案

调研日期：2026-11-12，Asia/Singapore。依据包括学校官方规则、当前账号的只读 Slurm 查询、`sbatch --test-only` 测算，以及 MLEvolve 原始代码。测算没有提交实际作业，也没有申请付费资源。

## 推荐判断

起步资源建议为 **1 张 A40 48GB + 8 CPU + 64GB RAM + 50–100GB SSD 工作空间**。先把单次 Agent 运行安排为 2–4 小时，实际实验量明确后再扩展到 8–12 小时。LLM 使用课程允许的 Qwen / DeepSeek API；训练 GPU 用于分类模型。更大的图像模型、batch 或显存需求出现后，再申请 A800 80GB。

学校训练环境已实际跑通，资源容量适合这一规模。但当前普通队列很拥挤，不能依赖每轮实验快速获得新分配。一次申请持续覆盖整轮 Agent 搜索，候选方案在同一作业内执行；本机用于交互开发、监控与必要的 API 控制。这个执行方式是建议，尚未实现 Agent。

关键规则：

- 当前提交入口强制 **每 GPU 最多8个CPU核**。本次 1 GPU / 16 CPU 请求在四个常规 GPU 队列均被拒绝，调整到8 CPU后全部通过校验。
- debug 官方定位是代码调试免费试用，单作业最长30分钟；不能用它规划一轮12小时正式 Agent 运行。
- 公开存储免费额度为 SSD 200GB/人、HDD 1TB/人。已配置环境约6.4GB，另有约3.3GB缓存；本项目起步50–100GB工作空间较合适。文件系统总空闲量不等于个人配额。
- 官方提供8卡GPU整机包机，A40类192元/天、A800类480元/天，至少按一天计费。当前单卡需求优先按卡时申请；整机包机更适合已有明确多卡并行任务的情况。
- 容器门户此前列过 A800 MIG 10/20/40GB。本次重新登录后，创建表单的集群列表没有成功加载，因此未确认当前可分配量。MIG 容器仍是待验证选项，不作为已经可用的运行条件。

## 为什么单卡适合 MLEvolve 类系统

[MLEvolve 原始配置](https://github.com/InternScience/MLEvolve/blob/main/config/config.yaml)默认 `num_gpus: 1`、`parallel_search_num: 3`、`cpu_number: 21`、运行时间43200秒。其[启动脚本](https://github.com/InternScience/MLEvolve/blob/main/run_single_task.sh)同样设置12小时与21 CPU，并调用模型 API。由此可见，多个规划/编码分支可以配合一张训练 GPU；较大的资源需求主要来自候选模型训练和多个试验的执行方式。

对本项目的初步适配建议：

1. 按 Slurm 实际分配的8 CPU核及 CPU affinity 设置线程数，GPU绑定沿用已验证的 UUID 逻辑，替换原脚本固定的资源参数。
2. 先保持一张训练GPU，GPU密集候选串行执行；规划与编码可异步，CPU候选并行数按实际线程和内存限制控制。
3. 一次分配内完成数据检查、实验、结果反馈、改进与产物保存，减少调度往返；每个候选保留独立日志、超时和可恢复结果。
4. 先为预训练权重准备本地缓存和同步路径。HPC访问 Hugging Face 受限，环境安装已经改用校内软件镜像。
5. 将论文12小时/500步配置视为参考；搜索规模、LLM记账、测试集边界及最终模型选择按课程要求与后续 SPEC 设计。

当前实际推荐：开发和小范围验证继续使用本机与学校 debug；正式运行首选单张 A40 的连续时段。普通队列若仍给出很远的预计时间，可在明确运行时限与计算预算后比较高优先级 A40，或询问学校是否能提供合适的预留时段。包机审批与额外算力购买属于后续选择，本次未办理。
